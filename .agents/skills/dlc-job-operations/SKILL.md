# DLC 任务操作

DLC 任务操作需要区分有效提交请求、平台任务状态和训练进程的实际进度。查询、预览、提交、续训和停止各有对应的操作条件与结果证据。

## 请求与提交

先看 `pai --help`、`pai dlc job --help` 和目标子命令帮助。优先使用项目已有 YAML/JSON；专用 CLI 简化配置与 CreateJob 原生请求体分别选择正确入口。缺少能力再查 `aliyun pai-dlc`，参数和请求格式以当前入口帮助为准。

- 确认目标工作空间、角色/副本数、输入制品、结果路径、训练入口、时限及结束保留设置。时限是上限，不是预计耗时或确定费用。
- 提交前确认输入制品可读、结果位置可写、镜像与所选 GPU/驱动兼容。请求预览只能检查请求，不能证明运行环境已经通过验证。
- 提交前查询相关任务；相似任务名不证明重复，比较有效请求、恢复来源和实验意图。
- 用官方 dry-run 检查最终请求，尤其是 CLI 覆盖后实际命令、配置和字段类型，保存脱敏后的有效请求快照。
- 提交后立即保存返回 JobId、请求与响应。响应超时或不明时查询并核实是否创建，不盲目重试；不能唯一识别时保留待核实状态。

## 续训

按明确的来源记录和项目恢复入口选择具体 checkpoint 或 run，核对项目支持的恢复格式与 checkpoint 完整性。不要用文件修改时间挑“最新模型”。

先检查训练参数语义：目标总轮数与额外轮数不同。若项目的 epochs 表示总轮数，已完成 1 轮、目标 20 轮应从第 2 轮运行至第 20 轮。没有恢复参数就是重跑，不能把它称为续训。

保持项目要求兼容的数据、模型及优化器相关参数。首次执行恢复后，核对日志中的实际起始 epoch/step；有恢复配置不等于真正恢复成功。新的 DLC 任务使用独立结果目录，保留来源 checkpoint 和实际恢复起点作为证据。

## 跟踪与诊断

| 观察 | 下一步 |
|---|---|
| Creating 且没有 Pod | 查任务状态和任务事件，不反复请求不存在的日志 |
| EnvPreparing / ImagePulling | 查 Pod 子状态和事件，区分调度、网络、拉镜像与挂载；无日志本身不是失败 |
| Running | 读训练日志，核对恢复起点、最新进度与 run_id，保存关键日志 |
| Failed / Stopped / 超时 | 保存终态原因及相关事件/日志，定位是否有完整 checkpoint |
| Succeeded | 核对实际完成进度，再取得结果完整性证据；成功状态不等于目标轮次已完成 |

优先使用 `job get`、`events`、`logs` 的过滤、tail、等待能力，参数按本机帮助确认。轮询间隔依据阶段选取，避免忙轮询。明确报告未开始训练、正在计算或正在归档，不用准备时间估算每轮训练速度。

状态快照应包含当前平台状态、训练阶段、最新可确认的进度及证据来源。终态验收还需核对实际完成进度和结果持久化情况。

## 终态与结果证据

平台终态、实际完成轮次、日志、最终/最佳 checkpoint 及完整性结论分别核对。任务结束状态与训练目标是否达成是两个独立结论。

故障诊断保留任务事件和相关日志。停止任务时使用已确认的 JobId；响应不明时先查询状态，再判断停止操作是否生效。

官方入口：[PAI DLC CLI](https://help.aliyun.com/zh/pai/developer-reference/dlc-distributed-training)、[OpenAPI](https://api.aliyun.com/)。
